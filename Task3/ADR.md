### <a name="_3bfxc9a45514"></a>**Функциональные требования**
Верхнеуровневые сценарии для MVP системы открытия депозитов:

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
|UC01|Потенциальный клиент|Просмотр депозитов на сайте|Пользователь заходит на сайт банка -> просматривает список доступных депозитов с актуальными ставками -> изучает условия|
|UC02|Потенциальный клиент|Подача заявки через сайт|Пользователь выбирает депозит -> заполняет форму (ФИО, телефон) -> отправляет заявку -> получает подтверждение|
|UC03|Менеджер кол-центра|Обработка заявки с сайта|Менеджер получает заявку в системе кол-центра -> связывается с клиентом|
|UC04|Существующий клиент|Просмотр депозитов в интернет-банке|Клиент авторизуется в интернет-банке -> просматривает персонализированные депозиты с индивидуальными ставками -> изучает условия|
|UC05|Существующий клиент|Подача заявки через интернет-банк|Клиент выбирает депозит -> указывает счёт списания и сумму -> подтверждает СМС-кодом -> отправляет заявку|
|UC06|Сотрудник бэк-офиса|Обработка заявки из интернет-банка|Сотрудник получает заявку -> проверяет данные -> оформляет депозит в АБС -> отправляет СМС-уведомление клиенту|
|UC07|Менеджер бэк-офиса|Управление ставками|Менеджер заходит в АБС -> изменяет ставки по депозитам -> публикует изменения для всех каналов|
### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**
Архитектурно значимые требования для MVP системы открытия депозитов:

|**№**|**Требование**|
| :-: | :- |
|NFR01|**Производительность**: Отклик системы по операциям должен быть в пределах 100 мс|
|NFR02|**Производительность**: Загрузка справочных данных должна происходить менее чем за 1 секунду|
|NFR03|**Надёжность**: Доступность сервисов должна составлять 99.9% (24/7)|
|NFR04|**Надёжность**: Система должна быть отказоустойчивой при сбоях в ЦОД|
|NFR05|**Масштабируемость**: Интернет-банк должен поддерживать горизонтальное масштабирование|
|NFR06|**Безопасность**: Обязательное шифрование трафика для защиты данных|
|NFR07|**Безопасность**: Соответствие требованиям ЦБ РФ по защите данных|
|NFR08|**Интеграция**: Интернет-банк, сайт, система открытия депозитов не должны работать напрямую с API АБС|
|NFR09|**Технологические ограничения**: АБС может масштабироваться только вертикально (Oracle)|
|NFR10|**Поддерживаемость**: Использование существующих технологий (MS SQL, Oracle, Kafka, .NET)|

### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Архитектурные диаграммы

**Диаграмма контекста C4**: [`c4_context_mvp.puml`](c4_context_mvp.puml)
- Показывает взаимодействие MVP системы открытия депозитов с внешними участниками и системами
- Определяет границы системы и основные потоки данных

**Диаграмма контейнеров C4**: [`c4_container_mvp.puml`](c4_container_mvp.puml)
- Детализирует внутреннюю структуру MVP системы, интернет-банка и АБС
- Показывает технологический стек и интеграции между компонентами

#### Архитектурное решение

**Основные принципы решения:**

1. **Микросервисная архитектура для MVP системы**
   - Сервис депозитов: обработка заявок и бизнес-логика
   - Рассчет ставок: будет производится в АБС, это ее ответственность
   - Сервис уведомлений: централизованная отправка SMS
   - API Gateway: единая точка входа с аутентификацией и rate limiting

2. **Асинхронная обработка через Kafka, защита АБС от перегрузки**
   - Разделение обработки заявок на открытие счета и рассчетов условия от АБС, защита АБС от перегрузки
   - АБС сообщает об обновлениях в справочных данных сервису депозитов

3. **АБС**
   - добавляется модуль рассчета ставок
   - добавляется обработка заявок из Kafka
   - Интеграция в сторону сервиса депозитов
   - Интеграция в сторону системы колл-центра 

#### Логика принятия технологических решений

**ASP NET для микросервисов:**
- Соответствует экспертизе команды (уже используется в интернет-банке)
- Хорошая поддержка интеграций и микросервисной архитектуры
- Возможность горизонтального масштабирования

**MS SQL для MVP системы:**
- Соответствует требованию использования существующих технологий
- Достаточная производительность для OLTP операций

**Apache Kafka для очередей:**
- Прямое требование из нефункциональных требований
- Обеспечивает надежность доставки сообщений
- Поддерживает высокую нагрузку

**API Gateway (Kong/Nginx/...):**
- Rate limiting
- Мониторинг и логирование всех запросов
- Задел под дальнейшие разработки

#### Покрытие сценариев

- **UC01-UC03**: Заявки с сайта обрабатываются через API Gateway -> Система кол-центра
- **UC04-UC06**: Заявки из интернет-банка обрабатываются через API Gateway -> Сервис депозитов -> АБС
- **UC07**: Управление ставками остается в АБС, но автоматизируется там же

#### Обеспечение нефункциональных требований

- **Производительность**: Кэширование, асинхронная обработка, горизонтальное масштабирование
- **Надежность**: Kafka для гарантированной доставки, мониторинг компонентов
- **Безопасность**: HTTPS, отсутствие прямых связей с АБС
- **Масштабируемость**: Микросервисная архитектура, Kafka, MSSQL (масштабирование на чтение)
### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Альтернатива 1: Монолитная архитектура
**Описание**: Создание единого приложения для обработки всех заявок на депозиты в АБС
**Преимущества**:
- Простота разработки и развертывания
- Меньше сетевых вызовов
- Проще отладка и мониторинг

**Недостатки**:
- Невозможность масштабирования отдельных компонентов
- Риск полного отказа системы при сбое
- Сложность внедрения новых технологий
- Высокий риск что нагрузка не будет выдержана

#### Альтернатива 2: Прямая интеграция интернет-банка с АБС
**Описание**: Модификация интернет-банка для прямой работы с API АБС
**Преимущества**:
- Меньше промежуточных слоев
- Более быстрый отклик

**Недостатки**:
- Нарушение требования NFR08 (интернет-банк не должен работать напрямую с АБС)
- Высокий риск перегрузки АБС
- Сложность контроля нагрузки

**Недостатки, ограничения, риски**

#### Недостатки выбранного решения

1. **Сложность архитектуры**
   - Увеличение количества компонентов требует более сложного мониторинга и управления
   - Сложность отладки межсервисных взаимодействий

2. **Производительность**
   - Дополнительные сетевые вызовы между микросервисами
   - Возможная задержка при обработке через очереди сообщений

#### Ограничения

1. **Технологические ограничения**
   - АБС может масштабироваться только вертикально (Oracle)
   - Ограниченная команда разработки
   - Зависимость от подрядчиков для интернет-банка и кол-центра

2. **Регуляторные ограничения**
   - Соответствие требованиям ЦБ РФ по защите данных
   - Необходимость аудита всех операций с депозитами

#### Риски

- **Высокий**: Перегрузка АБС при пиковых нагрузках
- **Средний**: Проблемы совместимости при интеграции с legacy-системами
- **Высокий**: Сложный, новый процесс для сотрудников банка


#### Меры по снижению рисков

1. **Поэтапное внедрение**: Начать с ограниченной группы клиентов, например только с клиентов банка
2. **Мониторинг производительности**: Внедрение мониторинга всех систем
3. **Обучение команды**: Тренинги по микросервисной архитектуре
4. **Контроль нагрузки**: Настройка rate limiting и circuit breaker
