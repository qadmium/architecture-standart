### **Решение**

#### Архитектурные диаграммы

**Диаграмма контекста C4**: [`c4_context_call_center.puml`](c4_context_call_center.puml)
- Показывает взаимодействие системы с внутренним и партнерским кол-центрами
- Определяет новые интеграции через Kafka и SFTP

**Диаграмма контейнеров C4**: [`c4_container_call_center.puml`](c4_container_call_center.puml)
- Детализирует архитектуру с новым SFTP-сервисом для партнерской интеграции
- Показывает потоки данных через Kafka для синхронизации ставок

#### Архитектурное решение

**Основные принципы решения:**

1. **Централизованная публикация ставок через Kafka**
   - АБС публикует все изменения ставок в Kafka topic
   - Все потребители (кол-центр, SFTP-сервис) подписываются на обновления
   - Гарантированная доставка и порядок сообщений

2. **Асинхронная обработка для защиты АБС**
   - АБС не блокируется при отправке ставок
   - Kafka обеспечивает буферизацию при недоступности потребителей
   - Возможность replay сообщений при сбоях

3. **Специализированный сервис-адаптер для партнерской интеграции**
   - Отдельный микросервис для работы с внешними партнерами
   - Преобразование данных из АБС\Kafka в файловый формат
   - Передача файлов по SFTP

4. **Модификация системы кол-центра**
   - Добавление Kafka consumer для получения ставок
   - Обновление локальной базы данных ставок
   - Интеграция с существующим UI для отображения актуальных ставок

#### Логика принятия технологических решений

**Apache Kafka для публикации событий изменения ставок:**
- Гарантированная доставка сообщений (at-least-once delivery)
- Высокая производительность и масштабируемость
- Возможность replay для восстановления после сбоев
- Поддержка множественных потребителей

**SFTP для партнерской интеграции:**
- Требование партнера - работа только с файлами
- Безопасная передача данных
- Простота реализации на стороне партнера

**ASP.NET для SFTP-сервиса:**
- Соответствие экспертизе команды
- Интеграция с Kafka через .NET клиенты

#### Покрытие сценариев

- **UC08**: Внутренний кол-центр получает ставки через Kafka в реальном времени
- **UC09**: Партнерский кол-центр получает ставки через SFTP-файлы
- **UC10**: АБС публикует все изменения ставок в Kafka
- **UC11**: Система кол-центра автоматически обновляет ставки
- **UC12**: SFTP-сервис обеспечивает передачу ставок партнеру

#### Обеспечение нефункциональных требований

- **Актуальность данных**: Kafka обеспечивает доставку в течение секунд, SFTP - в течение минут
- **Надежность**: Kafka гарантирует доставку, SFTP-сервис имеет retry механизмы
- **Мониторинг**: Логирование всех операций публикации и доставки ставок
- **Безопасность**: Шифрование в Kafka и SFTP, аутентификация партнеров

### **Альтернативы**

#### Альтернатива 1: Прямая интеграция АБС с кол-центрами
**Описание**: АБС напрямую отправляет ставки в системы кол-центров через API
**Преимущества**:
- Простота архитектуры
- Меньше промежуточных компонентов
- Прямой контроль над доставкой

**Недостатки**:
- Нарушение принципа защиты АБС от внешних интеграций
- Сложность масштабирования при добавлении новых партнеров
- Риск перегрузки АБС при недоступности партнерских систем
- Сложность обеспечения гарантированной доставки

#### Альтернатива 2: Синхронная передача через REST API
**Описание**: Создание REST API для передачи ставок партнерам в реальном времени
**Преимущества**:
- Мгновенная доставка обновлений
- Стандартный подход для API интеграций
- Возможность получения подтверждения доставки

**Недостатки**:
- Партнер не готов к API интеграциям (только SFTP)
- Необходимость обеспечения высокой доступности API
- Сложность обработки сбоев и retry логики
- Блокирующие операции при недоступности партнера

#### Альтернатива 3: Batch обработка через базу данных
**Описание**: Периодическая выгрузка ставок из АБС в файлы через scheduled job
**Преимущества**:
- Простота реализации

**Недостатки**:
- Нагрузка на АБС
- Поддержка механизма ложится на команду АБС

### **Недостатки, ограничения, риски**

#### Недостатки выбранного решения

1. **Сложность архитектуры**
   - Добавление Kafka увеличивает сложность инфраструктуры
   - Необходимость мониторинга дополнительных компонентов
   - Сложность отладки асинхронных процессов

2. **Задержка в SFTP доставке**
   - Партнерский кол-центр получает обновления с задержкой
   - Возможны расхождения в ставках между внутренним и партнерским кол-центрами

#### Ограничения

- Партнер работает только с SFTP, нет возможности API интеграции
- Ограниченные возможности по частоте обновления файлов
- Нельзя нагружать АБС


#### Риски

- **Высокий**: Недоступность Kafka приведет к остановке обновления ставок во всех системах
- **Низкий**: Сбои SFTP соединения могут привести к устаревшим данным у партнера
- **Средний**: Расхождения в форматах данных между системами

#### Меры по снижению рисков

1. **Обеспечение высокой доступности Kafka**: Кластер из 3+ узлов, репликация данных
2. **Мониторинг и алертинг**: Отслеживание доставки сообщений, состояния SFTP соединений
3. **Retry механизмы**: Автоматические повторы при сбоях SFTP передачи
4. **Fallback процедуры**: Возможность ручной передачи файлов при критических сбоях
